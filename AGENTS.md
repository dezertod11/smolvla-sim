## ПК-1 и Docker

- GPU: RTX 5070 Ti. Единственный используемый движок — Docker Desktop с WSL integration.
- Нативные `docker.service` и `docker.socket` в Ubuntu отключены и masked,
  `containerd.service` отключён. Не включай второй движок.
- Диск Docker: `D:\DockerDesktopWSL\disk\docker_data.vhdx`; Ubuntu WSL остаётся
  на C:. Код хранится в Linux-файловой системе WSL.
- HOME сохраняет путь `/data/home`, но смонтирован из Linux-тома `smolvla-sim-home`.
  VS Code Server и состояние Codex должны оставаться на Linux filesystem:
  Windows bind mount не поддерживает нужные Unix-сокеты. Старый `/data/home`
  на Windows сохранён как резервная копия и перекрыт томом. Том объявлен external
  и переживает `down -v`; не удаляй его вручную: там настройки и история.
- `setup/Open-PC1.cmd` открывает контейнер в отдельном профиле VS Code;
  launcher восстанавливает Docker-wrapper и исключает его из Settings Sync.
- Сеть VS Code/Codex: `remoteEnv` задаёт HTTP(S)-прокси
  `http://host.docker.internal:18089`. Это SSH-туннель к Happ на ноутбуке,
  которым управляет `setup/Start-PC1Proxy.ps1`. Ноутбук/Happ нужны во время работы.
  Не отключай TLS-проверки и не копируй auth.json для устранения сетевой ошибки.
  В обычном `docker exec` этих переменных нет; проверки через exec должны
  явно задавать HTTPS_PROXY. Подробности и откат: `setup/CODEX_NETWORK.md`.
- Из WSL управляй проектом через `bash scripts/pc1.sh ...`;
  `scripts/docker.sh` проверяет выбранный движок.
- Образ `smolvla-sim:dev` уже собран. Обычный запуск использует
  `pull_policy: never`; build вынесен в `compose.build.yaml`.
  Если образ не найден, сначала диагностируй движок и хранилище.
- Изменение Python-кода не требует пересборки. Перед сборкой или большой
  загрузкой проверяй `df -h /mnt/c /mnt/d` в WSL: виртуальное свободное место
  Linux FS не равно запасу на физическом Windows-диске.
- Веса, датасеты, кэши и результаты — в `/data`, не в образе или Git.
  Полный LIBERO требует расчёта места; основное обучение предусмотрено на H100.
- Не очищай чужие контейнеры, Jupyter, учебные окружения и резервные копии.
  Глобальные prune/reset, остановка всей WSL и удаление старых хранилищ
  не входят в обычную разработку проекта.

## Проверки

В контейнере, из `/workspace`:

```bash
python -m pytest -q
ruff check .
```

После изменений среды или интеграции, по необходимости:

```bash
bash scripts/check.sh
bash scripts/check_ros_package.sh
bash scripts/eval_reference.sh
```

Последняя команда запускает один reference-эпизод и может скачать веса.
`check_ros_package.sh` проверяет инфраструктурный пакет, не рабочий контур
управления политикой. `check.sh` уже включает pytest и Ruff.
Из WSL: `bash scripts/pc1.sh exec -T dev bash scripts/check.sh`.
На H100: `.venv/bin/python -m pytest -q` и `.venv/bin/ruff check .`.
Выбирай проверки по изменению; документация не требует обучения или GPU-прогонов.

## Реализация, эксперименты и Git

- Сохраняй закреплённые версии; ревизии моделей/данных — `configs/artifacts.json`.
  Изменения зависимостей отражай в `.in` и соответствующих lock-файлах.
- Сравнивай собственную и reference модели на одинаковых задачах и начальных
  состояниях. Всегда явно задавай `n_action_steps`. Один успешный эпизод —
  smoke-проверка, не оценка success rate.
- CUDA-проверка bitsandbytes не доказывает квантизацию всей политики.
  Фиксируй реальные dtype, warmup, CUDA sync, p50/p95 и условия замера.
- Не включай в Git веса, датасеты, токены, ключи, `.env` и runtime-артефакты.
- Текущий `origin` обслуживает внутреннюю синхронизацию через ПК-1, это не GitHub.
  Не заменяй его без учёта `setup/Sync-PC1.ps1`.
- Не перезаписывай незакоммиченные изменения и не применяй force-push/reset для синхронизации.
  Ноутбук ↔ ПК-1: `setup/Sync-PC1.ps1` / `-Pull` после коммита.
  ПК-1 → H100: `bash scripts/sync_h100.sh` из чистой ветки main в WSL.
- После этапа обновляй `docs/STATUS.md`: результат, проверки, пути к доказательствам,
  ограничения и следующий шаг. При изменении запуска обновляй README.
  Исходный текст `docs/TASK.md` сохраняй; новые решения записывай отдельно.
