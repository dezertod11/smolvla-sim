# Автономное выполнение задания

Управляющий — текущий desktop-чат Codex. Он выполняет работу через SSH на ПК-1
и H100. VS Code остаётся редактором; другой агент не должен одновременно
редактировать проект или запускать эксперименты. Пользователь подтвердил,
что прежний агент VS Code уже не работает. Передача управления возможна через
`docs/VSCODE_HANDOFF.md`, после остановки управляющего desktop-чата/его расписания.

Исходное задание: `docs/TASK.md`. Текущие доказательства: `docs/STATUS.md`.
Бюджет: `docs/RUN_BUDGET.md`; без явного согласования пользователя обучение,
включая короткий training smoke, не запускать. `approved=false` по умолчанию.

## Исполнение

Основное обучение — одна свободная H100 2–7. GPU 0 запрещена, 1 только eval/smoke.
ПК-1 — ROS2, локальная оценка, демонстрация. Обучение на ПК-1 требует отдельного
бюджета: сейчас ему выделено 0 запусков. Занятую GPU не освобождать принудительно.
На проверке 12 октября RTX 5070 Ti использовала около 6 ГБ; H100 2–7 были свободны.

`scripts/jobs.py` сохраняет исходники, их SHA256, исходный Git commit, команду,
конфиг бюджета, журнал, статус, heartbeat и код завершения каждого запуска.
Supervisor запускается отдельным сеансом Linux, stdin закрыт: закрытие SSH
не прерывает работу. Перезагрузка сервера/контейнера не переживается автоматически.
После устаревшего heartbeat сначала разобраться с процессами; не менять статус
на успешный и не запускать дубликат. Resume обучения — отдельный проверенный
этап из сохранённого checkpoint, пока автоматически не реализован.

Один активный managed job на машину. Ограничение распространяется на наш
менеджер, не резервирует GPU от других пользователей. После выбора GPU сохранить
её физический индекс. Все последующие запуски проверяют занятость заново.
Таймаут завершает только группу процессов своего запуска. Отмена идёт через
cancel.request, без убийства произвольного PID из старого файла.

Лимиты учитываются консервативно: каждый submit резервирует весь timeout,
даже если завершился раньше или с ошибкой. Повторный ID запрещён. Если бюджет
исчерпан, запросить изменение с объяснением; не обнулять историю для обхода.
Менеджер — защита от случайных повторов, не sandbox для недоверенного кода.

## Команды

В контейнере VS Code (ключи SSH и Docker socket сюда не передаются):

```bash
python scripts/control.py h100 status
python scripts/control.py h100 submit configs/jobs/h100-train-smoke.json
python scripts/control.py h100 logs h100-train-smoke-001
python scripts/control.py h100 cancel h100-train-smoke-001
python scripts/control.py pc1 status
```

До утверждения бюджета submit GPU-задачи должен отказать. Worker работает в WSL
ПК-1, tmux `smolvla-control`. Восстановление после перезапуска WSL:
`bash scripts/start_control.sh`. Launcher ноутбука также запускает его.
Из WSL эквивалент: `bash scripts/experiment.sh h100 status`.
Синхронизация чистой ветки main: `python scripts/control.py h100 sync`.
После таймаута запроса исход неизвестен: сначала проверить status/response,
а не повторять submit. Ответы остаются в `.runtime/control/responses`.

Запуски H100: `.runtime/runs/<id>` внутри разрешённого проекта.
Запуски ПК-1: `/data/runs/<id>`. Данные/модели не включаются в снимок исходников.
Копия budget approval — `.runtime/approved-budget.json` на соответствующей машине.
Утверждение относится к одному пакету лимитов; не создавать новые каталоги runs
для сброса счётчика.

## План по критериям приёмки

1. Проверить закреплённые артефакты, транзитивный VLM/tokenizer, пути кэшей,
   место и download выбранных 454 эпизодов. Полный LIBERO без нужды не скачивать.
2. После согласования бюджета: 50 шагов, загрузка реального batch, forward/backward,
   checkpoint/reload; число trainable parameters, фактические dtype, GPU memory,
   шагов/сек. По измерению скорректировать 30k шагов/batch16 в пределах лимита.
3. Обучить основной вариант. Реализовывать ROS2/тесты в отдельной рабочей копии
   исходников, пока обучение использует собственный снимок. При ошибке сначала
   читать логи, изменить конкретную причину, не повторять неизменённую команду.
4. Оценка: 10 задач × 10 эпизодов на вариант, общие seed/начальные состояния,
   checkpoint hash, явные n_action_steps. Матрица: reference/10, own BF16/10,
   own BF16/1, own BF16/50, own INT8/10. Это минимум 500 эпизодов, не 5 smoke.
   Для настройки использовать отдельный небольшой набор; финальные seeds зафиксировать.
5. Latency CPU/GPU: реальные dtype, warmup, CUDA synchronization, p50/p95,
   размер сериализованной модели и peak memory. INT8 kernel smoke не доказывает
   квантизацию политики: фиксировать преобразованные/непреобразованные модули,
   проверить загрузку и качество тем же протоколом. Честно указать ограничения.
6. Реализовать sim_node и неблокирующий smolvla_node, параметры YAML, launch,
   watchdog отсутствующих данных, тесты mock-policy. Финальный Compose должен
   запускать реальные эпизоды, а dev-профиль сохранить для редактора.
7. Видеодоказательства, таблицы README, loss plot, отчёт на страницу, объяснение
   Jetson Orin и SO-101. Проверить сборку/старт на чистом окружении с учётом диска.
   GitHub CI считается выполненным только после реального успешного запуска.
   Репозиторий/публикацию согласовать отдельно, если аккаунт или видимость неизвестны.

## Проверки по расписанию

Проверять работу примерно раз в 15–30 минут и при завершении своих команд.
Никаких автоматических повторов обучения по одному наличию ошибки/низкого loss.
Каждая проверка: жив ли job, двигается ли step, конечен ли loss, хватает ли места,
есть ли checkpoint, не появился ли результат для следующего этапа.
Если существенных изменений нет — без сообщения пользователю. Сообщать о
завершении этапа, ошибке, исчерпании бюджета или необходимом решении.
Планировщик не должен запускать второго владельца проекта параллельно с IDE.
Расписание само по себе не гарантирует качество: завершение сверять с TASK.md.

Сеть агента пока зависит от ноутбука/Happ. Обучение на H100 от ноутбука не зависит.
Пока ноутбук спит, управляющий агент не сможет проверять и менять эксперимент.
